# Reference system

A neutral multi-controller system used as the walkthrough and the subject of milestone exit criteria ([ADR-0004](../../docs/adr/0004-reference-system.md)). [docs/adopt-owned-project.md](../../docs/adopt-owned-project.md) uses it as its example. Three controllers interact only through Kubernetes resources in the `refsystem.example.org` group:

| Kind | Spec | Status | Owned by |
| --- | --- | --- | --- |
| `Tenant` | `quota` | `namespaceReady` | tenant controller |
| `Database` | `tenant`, `size` | `ready`, `secretName` | database controller |
| `Backup` | `database` | `phase` | backup controller |

- `api/v1alpha1/`: Go types, scheme registration and generated deepcopy methods.
- `config/crd/`: CRD manifests generated by `make api-generate`.
- `config/discovery/`: a discovery snapshot of the built-in kinds the controllers use.
- `controllers/`: the three controllers and their fake-client tests.
- `generated/`: the committed output of `arch extract`.
- `project.yaml`: the project document that selects the API types and the controllers.
- `abstraction.yaml`: the abstraction document. It declares one object of each kind the controllers read or create, and the fields they touch.
- `internal/extractcheck/`: runs the extractor over one controller package; each controller test uses it to prove that the controller extracts with no diagnostic.

## Controllers

| Controller | Creates | Watches | Requeue |
| --- | --- | --- | --- |
| tenant | a `Namespace` named after the Tenant, and a `ResourceQuota` in it with a hard limit of 10 pods | `Tenant` | none |
| database | a `Secret` named after the Database, beside it | `Database`, owned `Secret`, `Tenant` through the Databases labelled with its name | none |
| backup | a `Job` named after the Backup, beside it | `Backup`, owned `Job`, `Database` through the Backups whose `spec.database` names it | 30 seconds while the Job runs |

## Owner references

Kubernetes accepts an owner reference only when the owner is cluster-scoped
or lives in the same namespace as the dependent. The controllers follow that
rule:

- The tenant `Namespace` has no owner. A Namespace is cluster-scoped and a
  Tenant is namespaced, so the Tenant cannot own it. For the same reason the
  tenant controller has no owner watch: no event on the Namespace would map
  back to the Tenant.
- The `ResourceQuota` lives in the tenant namespace, not beside the Tenant.
  The Namespace owns it, through `controllerutil.SetOwnerReference`.
- The `Secret` lives beside its Database, which controls it through
  `controllerutil.SetControllerReference`.
- The `Job` lives beside its Backup, which controls it through
  `controllerutil.SetControllerReference`.

## Extraction

From the module root:

```sh
go run ./cmd/arch --project examples/refsystem/project.yaml --out examples/refsystem/generated extract
```

`arch extract` finds the three controllers and their seven watches:

| Controller | Watch | Mapping |
| --- | --- | --- |
| backup | `Backup` | self |
| backup | `Job` | owner `Backup` |
| backup | `Database` | `reference`: the Backups whose `spec.database` is the Database's name |
| database | `Database` | self |
| database | `Secret` | owner `Database` |
| database | `Tenant` | `label`: the Databases labelled `refsystem.example.org/tenant=<tenant>` |
| tenant | `Tenant` | self |

It reads all three `Reconcile` methods with no unsupported construct. The
abstraction selects every field the methods read or write, so no field is
`unresolved` and `--strict` passes. Without it, 39 fields are unresolved.
`arch generate` composes the three controllers from their declarations in
`project.yaml` (see below). `cmd/arch` checks that the committed files match
a fresh run. [docs/supported-patterns.md](../../docs/supported-patterns.md)
lists the constructs the controllers use.

## Known extractor gap

The Secret has the Database's name. A name such as
`database.Name + "-credentials"` reads better, but the extractor cannot yet
lower a string concatenation with a field. The controller keeps the bare
name until it can.

## Composed model

Each controller is declared under `spec.controllers` of `project.yaml`: its
key object, one effect per client method and kind, and the initial value of
every abstracted field. `arch generate` composes the three models into one
(`composition.yaml` lists the components and the derived bindings), and
`arch check` samples it:

```sh
go run ./cmd/arch --project examples/refsystem/project.yaml --out examples/refsystem/generated generate
go run ./cmd/arch --project examples/refsystem/project.yaml --out examples/refsystem/generated check --samples 60 --steps 150
```

The reads keyed by `client.ObjectKey` literals, such as the Namespace named
after the Tenant, resolve through the abstraction, whose identity fields
fix each object's name. The generated files are not committed; `cmd/arch`
generates the system in its tests. `spec.boundaries` adds the Flux
Kustomization boundary (`boundaries/flux`, a copy of the library's) as an
assumed component that applies the Tenant, Database and Backup manifests,
so each owned kind binds to it as well. The boundary's own model, the
periodic apply and the Ready condition, runs beside the controllers, and
`arch check` lists its five assumptions in the report.
